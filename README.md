# zonewright

MCP server through which Claude manages and works in Blender to build EverQuest zones.

## Install (Windows)

Requires Python 3.14 on PATH as `python`, git, Claude Code, and Visual Studio 2022 (Community will do) with the "Desktop development with C++" workload and its "C++ CMake tools for Windows" component, with which `syncTooling` builds the Recast helper.

From the root of a clone of this repository, in PowerShell, with a clone of rbraunm/mcps for facet's client (zone deployment reaches the test server through it):

```
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python -m pip install -e <mcps clone>\facet
$env:zonewrightEverQuestClient = '<EverQuest client folder>'
.venv\Scripts\python -m pytest
claude mcp add --scope user zonewright --env zonewrightEverQuestClient=<EverQuest client folder> -- "$PWD\.venv\Scripts\python.exe" "$PWD\server\zonewrightServer.py"
```

`zonewrightEverQuestClient` is the one setting that differs by machine: the EverQuest client folder, holding `eqgame.exe`. The tests refuse to run without it. The server starts without it, and each tool that reads the client refuses, naming it.

Tests run against the real pinned Blender through the real bridge. That Blender is installed once by `syncTooling` under `%LOCALAPPDATA%\zonewrightTests\<pin>` and shared by every test session in every worktree; each session has its own tooling root whose `blender` folder links to it. The Recast helper is built into the same shared install, once per fingerprint (each worktree's sources build their own and never remove another's), and each session's `recast` and `recastHelper` folders link to it. One server and Blender stay running for a session, each test starting from an empty file; a test that needs a process of its own (a crash, a code change, the machine profile) takes `freshBlenderServer`. Sessions running at the same time each need their own short `--basetemp`: pytest prunes its shared temp folder, and long paths break Blender.

The suite runs in three tiers. Everyday tests (the tools on small built scenes, and the server and bridge lifecycle) always run. The client data tier checks the client's own data in three groups: surveys of client zones, reading client models, zones, emitters, and the zones `eqgame.exe` registers (with Highpass Hold's server rows written from them), and calibration against screenshots; and the server's own data in two: `serverMaps`, the server map files against Peridot's own and Highpass Hold's player lane from its safe point; and `serverNav`, Peridot's Highpass Hold and thulehouse2 navs rebuilt tile for tile and Highpass Hold's NPC islands and path probes, both from EQEmu's map pack at a pinned commit, fetched once into `%LOCALAPPDATA%\zonewrightTests\serverReference` and verified by hash. The install tier installs Blender, extensions, and the Recast helper for real, over the network. A run of the whole suite takes a heavy group only when a file its tests depend on (the code they check, every server module that imports but the plumbing every test runs, the references they compare against, the Recast helper's sources and build where they run it, and the test modules holding them with the test helpers those import, found as the suite is collected) changed since the branch left the last pushed `claude` (`heavyGroups` in `tests/conftest.py`), and says at the end which groups ran and why. `-m clientData` or `-m install` runs a whole tier, `--everyTier` runs everything, and naming a test file runs all of it.

`claude mcp list` then shows `zonewright` as connected. Its tools are available in any session; the `zone-survey` skill loads in sessions started from the repository root.

## Tooling

`toolingManifest.json` pins Blender and every extension: version, download URL, and SHA-256. `syncTooling` makes `%LOCALAPPDATA%\zonewright` match it. Blender runs in portable mode (a `portable` folder next to `blender.exe`), so it never reads or writes the config of any Blender installed for personal use. Logs go to a file a day under `%LOCALAPPDATA%\zonewright\logs` (`zonewright.<date>.log`), which every server process appends to and none renames, and are kept 90 days.

To upgrade Blender, update the version, URL, and SHA-256 (from the release's published `.sha256` file) and run `syncTooling`.

### Machine profile

Performance settings are discovered per machine, never configured by hand. `syncTooling` ends by profiling the machine whenever `machineProfile.json` (under the tooling root) is missing or stale: it benchmarks a multi-material EEVEE render on each Blender GPU backend (Vulkan, OpenGL), rejects software renderers, and keeps the fastest hardware backend. Parallel CPU work uses 80% of the logical processors. The profile records the Blender version and a hardware fingerprint; when either changes, Blender tools fail until `syncTooling` re-profiles. `profileMachine` re-measures on demand. On the development machine (RTX 2080 Ti) Vulkan won: warm renders take about 0.1 s, and its shader cache survives Blender restarts, so a known scene's first render takes under a second instead of 18 s on OpenGL.

| Tool | Does |
|---|---|
| `getToolingStatus` | Reports Blender (`missing`, `broken`, `versionMismatch`, `installed`), each pinned extension (`missing`, `versionMismatch`, `installed`), installed extensions that are not pinned, and the Recast helper (`missing`, `stale` when only other fingerprints are built, `built`; with its fingerprint, commit, and compiler), and each calibration shot's latest `calibrateShot` run |
| `syncTooling` | Installs the pinned Blender after verifying its SHA-256, removes other Blender versions, installs, upgrades, or removes extensions to match the manifest, and fetches the pinned Recast tree and builds the helper when the current fingerprint has no build. Fails if Blender is running from the tooling root, if the pinned install is `broken` or `versionMismatch` (clear it by hand), if the Recast tree does not match its pin, or if Visual Studio lacks the C++ workload |
| `addExtension` | Pins the newest extensions.blender.org release of an extension compatible with the pinned Blender, then syncs. Fails if a different `version` is requested |
| `removeExtension` | Unpins an extension, then syncs to uninstall it |
| `profileMachine` | Re-measures the machine: CPU workers and the fastest hardware GPU backend for Blender |

### Recast helper

The server's nav meshes (`.nav`) are built and inspected by `recastHelper.exe`, a small C++ program in `recastHelper/` written against Recast and Detour (Zlib licence). `toolingManifest.json` pins EQEmu's recastnavigation fork at `710dabe`, the commit whose builds reproduce Peridot's nav polygons, with a SHA-256 of the extracted tree: GitHub does not keep its zips byte-stable, so the tree is verified, not the download. `syncTooling` fetches that tree from codeload into `%LOCALAPPDATA%\zonewright\recast\<commit>`, finds Visual Studio with `vswhere` (never a hard-coded path; it refuses, naming the workload, when the C++ tools or CMake are missing), and builds the helper with Visual Studio's own CMake and Ninja (`/O2 /fp:precise`, static runtime) into `recastHelper\<fingerprint>\`. The fingerprint covers the helper's sources, the tree, the compiler's version line, and the configure arguments, so a change to any of them makes a new build; older builds stay. On the development machine a build takes about 5 s, and Highpass Hold's nav builds in under a second on 12 threads (80% of the logical processors). Tools that need the helper refuse until it is `built`. The Visual Studio lookup behind the fingerprint (about 1.5 s) runs once per server process, so a Visual Studio update shows as `stale` after the server restarts.

`server/serverNav.py` drives it. Nav mode builds a zone's `.nav` (`navBytes`) from the collision the server rebuilds from its `.map` and the records of its `.wtr`, with map_edit's default settings (`serverNavSettings`, which describe the NPC, never the player) and the collidable extents as bounds, each tile on its own thread and added in grid order, so the file is byte-identical run to run. It refuses what map_edit or the server would drop without a word: over 16,384 tiles, a tile past its polygon bits, a tile past Recast's vertex limit (`rcBuildPolyMesh` refuses it), a vertex at or below z -15000, a Normal water region (map_edit marks it Recast's null area and cuts a hole in the nav), a region type no nav area maps, and a turned region (zonewright writes none, and map_edit can take a turned box's height range wrongly). Every `.nav` is read to its last byte by `serverMapFiles.readNav`, and the helper's payload is read the same way before it is written: a payload must end with its zlib stream, and each tile's size must be the one its header counts. Inspect mode loads a `.nav` as the server does, each tile at the slot its stored reference names (refusing a zero tile reference or size, a tile shorter than its header counts, or a tile `addTile` rejects), labels its polygons into components across links under the server's ground filter, reports every island apart from the safe point's piece with its snap risk, and searches paths to given points with Peridot's limits (1,024 nodes, a 256-polygon path); without a safe point it names the points it could not search from. It lists every polygon with its area, component, outline, and corners' heights, from which `serverMapDrawing.drawNav` draws plans by nav area, by component with the islands numbered, and of the polygons that differ from another nav.

Reach mode computes the player's lane (`server/playerReach.py`, which `mapReach`, `traceReach`, and the lane layers of `renderSketch`, `renderSection`, and `renderView` draw): every place players reach from where they arrive, by the moves docs/zoneWorkflow.md (Player space) lists, from what the zone ships and the client collides with. The helper rasterizes a grid of columns tile by tile on the profile's threads (Recast's heightfield; faces of either winding walkable up to `walkableNormalZ`, a boundary's walkable faces kept apart from the floor's; each kind of face, the floor's walkable, a boundary's walkable, and the rest, rasterized into a heightfield of its own and the helper merging their spans, so a merged span takes the area of the faces whose tops lie within the climb of its top whatever order the faces come in, where Recast's own merge raises a span's top before comparing tops and can carry a floor's area up a wall; then Recast's low-hanging-obstacle rule), takes every open interval of a column as a floor node and the part of it each swim box holds as a wet node, shallow where the water, up to the top of the boxes touching one over another there, stands no deeper than `minimumSwimDepth` over the interval's floor, and floods them: at the body group's height from every seed (walk, swim, and slide), the group wading shallow water on its floor, at the containment headroom for what only a smaller player passes (squeeze), swimming in a box at any depth since a smaller race may float in shallower water, from the safe point first so connected entries are known, back from the safe point and from every seed and zone line for the traps, and through open space at any rise from everything reached, which tells floor open space joins to the lane from floor sealed inside a closed solid; each pass a level at a time, the earliest node of a level taking any node it reaches first, so the lane file is the same run to run. Every move onto floor under the underworld, a walk or slide within the step as well as a fall, is recorded as a leak and goes no further. The lane is kept under `%LOCALAPPDATA%\zonewright\reach\<work file>-<hash of its path>` by a key of the helper's build, the grid, the movement, the triangles and which are a boundary's, boxes, zone lines and their landings, the seeds, and the underworld, so an unchanged zone's lane is reused (the newest three are kept).

The grid (`playerReach.reachGrid`: columns 1 across, centered on whole coordinates, cells 0.25 tall, tiles of 256 columns) was chosen by measuring the helper cold on the development machine (12 threads). Columns are centered on multiples of their size because blocks and walls are placed on whole units: a face on a whole coordinate runs through a column's middle, where one on a column's edge would fill the column beyond it as a one-column rim at its top, on two sides of every block only:

A column of 0.5 reaches what one of 1 reaches at four times the time and memory, past 30 s and 2 GB on the canyon; columns of 4 and 8 cut every face steeper than about 51 and 32 degrees, whose rise across a column passes the medium group's 4.95 step (an 80 degree face rises 22.7 and 45.4), and close every gap under 8 and 16. At 1 an 80 degree face rises 5.7 a column, so walkable faces whose rise across a column passes a group's step are cut there too (steeper than about 71, 79, and 79 degrees for the small, medium, and large groups), and a riser a group climbs rises no more across a column than a face it walks, so traceReach shows no climb of steps, and a gap of 2 always keeps an open column. Rasterizing is 1.2 s of the canyon's 14: the floods, which are global, take the rest, so no per-tile cache is kept (a local edit's recompute is the whole run). `mapReach` on the canyon copy computes its lane in 19 s (the bridge collecting the collision, the helper with its five floods, and reading it) and reuses it in 0.2 s; judging it against the regions and drawing its plan take 11 s and 1.3 GB more in the server.

## Scale

Blender scenes are authored at **1 Blender unit = 1 EQ unit**, Z up, in the zone files' own axes, so client models and zone files load unchanged. The server, and so the live dumps, give positions as (x, y, z) with x and y swapped against the zone files: Blender = (y, x, z), measured by every dumped door, ground object, and spawn landing on its zone's geometry only that way. `/loc` prints the server's y, x, z, which is Blender's x, y, z in order. Spawns draw at the client's scale for their height (see "Spawn size" under Client models): a dark elf female of the race-default height 5 stands about 6.5 units tall in a zone without `NewEngineZone` and about 5 in one with it. Eye-level views put the eye at a body group's eyeHeight above the ground (5.96 for the medium group; see below).

Players are judged as the bodies they play, from `server/playerScale.py`. Every playable race and gender (16 races, 32 bodies) is a body read from the client's data: its spawn height (the server's `GetRaceGenderDefaultHeight`, EQEmu `common/races.cpp:1489`; a player's own spawn goes out with size 0 and claudelink's dumps hold 6 for a human male and 5 for a dark elf female), the model eqgame.exe registers for it posed in its stand at the classic scale for that height (EQEmu sends `NewEngineZone` false for every zone), and that model's height, width side to side, and `avatarHeight`; `tests/testPlayerBodies.py` reads them again from the client. The bodies fall into three groups that do not overlap in height:

| Group | Races | Model heights | Walked bodies | playerHeight | playerWidth | stepHeight | Steepest | minimumSwimDepth | Eye |
|---|---|---|---|---|---|---|---|---|---|
| `small` | gnome, halfling, dwarf | 3.84 to 5.22 | dwarf male, gnome female | 5.5 | 2.5 | 2.97 (derived) | 80 (at least) | 2.17 | 3.67 |
| `medium` | human, erudite, wood elf, high elf, dark elf, half elf, iksar, froglok, drakkin | 5.92 to 8.07 | drakkin male, wood elf female, human male | 7.75 | 4.0 | 4.95 | 80 (at least) | 3.45 | 5.96 |
| `large` | barbarian, vah shir, troll, ogre | 8.55 to 11.65 | ogre male, vah shir female | 10.5 | 5.25 | 5.30 (at least) | 80 (at least) | 4.68 | 8.25 |

Frogloks stand in their bind pose (no archive the client links at startup holds their stand), arms out, so they never limit a group. Each group holds one set of measures, each with its source (`sources`: measured, with how, where, and when; unmeasured, with why the value; or derived, from what). The clearance and climbing measures come from the measurement zone (design #10, `measurementZone/`) walked on 2026-10-12 by the spare RoF2 client with claudelink's `walkMeasurementLanes` at a high frame rate (MacroQuest's frame limiter suspended, about 190 to 230 fps), as each group's sample (`sampleRoles`): its tallest and shortest body by avatarHeight, the height the client's walks follow, and its widest and thinnest by model width, the owner choosing among bodies that tie. Each is walked by a permanent character of its real race and gender, `Measure<code>` (claudeperidot ledger 20261012-233442 and its predecessors; a `#race` illusion leaves the client's avatarHeight at the human's), and the source files are claudelink's `%LOCALAPPDATA%\claudelink\measurements\<body>_20261012-*.json`. Per body, `walkedBodies` keeps the bracket each lane gave; a group takes the strictest of its walked bodies: `playerHeight` the most headroom one needed (the lowest ceiling it passed), `playerWidth` the widest passage, `stepHeight` the least riser climbed, `walkableNormalZ` the gentlest steepest ramp (and derived from it `steepestWalkableDegrees`; every group's is the course's steepest, 80, a lower bound), `minimumSwimDepth` the deepest water over the bed walked before floating (so the lane errs toward swimming). What the walks showed:

- **Step follows avatarHeight.** The wood elf female (avatarHeight 3.125) climbed every riser to 4.95 and was stopped from 5.0, 1.58 times her avatarHeight; the human, drakkin, ogre, and vah shir climbed every riser to the course's highest, 5.30, and the dwarf and gnome were stopped by its lowest, 4.50. The small group's step is the gnome female's avatarHeight times the wood elf's ratio (2.97; the dwarf's by the same ratio is 3.96, also under 4.50), and the large group's is the 5.30 every one of its bodies climbed, its limit lying above. A human male walking shipped zones on 2026-10-04 was stopped by risers from 5.22, which the measurement zone's plain risers do not repeat.
- **Every body climbed every ramp** to 80 degrees, the course's steepest, so each group's steepest walkable face is a lower bound.
- **Swimming starts about 0.3 over avatarHeight** (2.18 for the gnome, 4.07 for the human, 5.81 for the ogre), and a swimmer's feet float just over avatarHeight under the surface.
- **Clearance:** ceilings stopped each body at about twice its avatarHeight (the human passed 7.25, the drakkin 7.75, the ogre 10.5), and openings at about its avatarHeight (the human passed 3.75, the drakkin 4.0, wider than the human's model, the ogre 5.25).
- **Frame rate changes the limits.** At the background frame rate (about 30 to 80 fps) the same bodies, walked the morning of 2026-10-12, stopped on ramps from 74 to 79 degrees and needed 0.25 to 1.0 more headroom (the gnome 0.25 less); the measures are the high-frame-rate walks.
- **The client's avatarHeight for an ogre is 5.5**, where the bodies' model data give 5.625; the large group's eye follows the model data.

`eyeHeight`, the eye of eye-level views, stays a design value (5.5 for a body of the walked human's avatarHeight, 3.75, scaled for each group by its tallest body's avatarHeight: 3.67, 5.96, and 8.25); the walks measured each body's first-person eye at about twice its avatarHeight (7.44 for the human, 11.16 for the ogres), which these views do not follow.

Where each group may go is design: the zone is built for every group unless `setZoneProperties` `builtFor` names fewer, and a region can name its own (`createRegion`/`editRegion` `builtFor`: a gnome quarter in a human town, a giants' hall in a gnome town). A spot is judged by its region's groups, else the zone's: a group it is built for that cannot pass is a failure, any other group a finding. Every tool that judges where players stand, step, climb, swim, or fit reports which groups pass: `mapReach` floods a lane per group and judges each problem so; `traceReach` and `viewFromLane` trace and stand one group's players (`bodyGroup`); `walkRoute` walks each group, height, width (a `narrow` opening), step, and slope, and judges each problem where it lies; `placeEntry` refuses a footing only a group the spot is built for cannot arrive on and returns the others as findings; `buildSwimVolumes` counts the cells each group swims and wades; and what a build must suit (`gradeRoute`'s grades and ledge benches, cave grades, mouths, ends, and a branch's start over its parent, stair risers, walkway and deck grades, rock over a span's end, structures' walk lines) is judged for every group its place is built for (the least step and slope, the most clearance among them). Pictures take one group's eye or lane: `bodyGroup` where a tool takes one, else the middle of the groups the zone is built for for an eye (the medium group's 5.96 when it is built for all) and the group with the most clearance for a lane plan. The survey describes client zones as the medium group meets them. What judges how a thing looks or is built (a kit piece, deck, flight, wall, or floor standing off the ground; ground through a floor; a cave floor hanging; a cave wall's straight part over a raised foot; a plot standing on a cave floor stroke; a cave branch cutting a trench through its parent's rubble or pad; where a ground border wants a transition strip) takes tolerances of its own from `server/buildTolerances.py` (2 off the ground; ground no steeper than 60 degrees; ground probed from 2 over a part; a sight clear to 2 short of its point, a floor looked at from 1 over it), since a deck 4 over the ground reads as floating however high a player steps; the bridge's code and the tool descriptions both read them there.

The measurement zone (`measurementZone/`, design #10) is built with zonewright's own tools by `python measurementZone/buildMeasurementZone.py`: risers 4.50 to 5.30 by 0.05, ramps 70 to 80 degrees by 1, a pool whose bed falls 10 over 100 under a swim volume spanning it whole, a corridor whose ceiling steps down from 14 to 3 by 0.25, and one narrowing from 10 to 0.5 by 0.25, each labelled with its value and walked from one start line. It saves `%LOCALAPPDATA%\zonewright\measurementZone\arttest.blend`, exports the game export to `%LOCALAPPDATA%\zonewright\staging\arttest\` (the client's unused `arttest` slot, id 996), runs `verifyExport`, renders the course from above and at eye height, and writes `arttest_layout.json` beside the export, which claudelink's walk procedures read.

Zones export as EQG zones in these same units and axes: zonewright writes the .eqg itself, so no conversion applies (EQGZI's Blender exporter, by contrast, works at 1 Blender unit = 2 EQ units).

## Blender bridge

The first tool that needs Blender starts the pinned Blender headless (`--background --factory-startup`, portable config) running `server/bridgeMain.py`, which enables the pinned extensions and serves commands over 127.0.0.1 on a random port with a per-session token. Commands run one at a time on Blender's main thread. A refusal (a ValueError the bridge raises on purpose) comes back as its message alone; any other error, and any error in `runPython`'s code, comes back with its traceback. If Blender exits, the next call reports the exit code and Blender's last output, and the call after that starts a fresh Blender. Blender launches with the profiled GPU backend and 80% of the CPU for its threads and shader compilation. `syncTooling`, `addExtension`, `removeExtension`, and `profileMachine` stop an idle bridge first and refuse while the open file has unsaved changes.

Results come back as unindented JSON. The tools whose results run long (`walkRoute`, `gradeRoute`, `addShapingPass`, `setShapingPass`, `removeShapingPass`, `buildBridge`, `buildStairs`, `buildWalkway`, `buildWall`, `editStructure`, `cutCave`, `editCave`, `renderSection`, `checkExport`, `exportZone`, `verifyExport`, and `renderView` and `renderSketch` with the lane) write each result whole to `reports\<tool>\<UTC time>.json` under the tooling root (kept 90 days) and return a compact view naming it (`report`): walks without the body groups' measures and sampled profiles, a mesh's shaping passes as the pass the call touched, the active pass's name, and their count, long lists as their count and first three, findings by kind with the first of each, the lane and nav summarized, a `laneState` without the lane's constants, what it does not model, and its limits, and failures whole (`server/resultReports.py`).

Checkpoints are recovery points for when work goes badly wrong, not a way to iterate: passes, layers, and the region tools take decisions back. Each work file's checkpoints live in their own folder under the tooling root, named for the file and a hash of its full path, so work files of one name in different folders never mix and nothing is written into the work repository.

Nothing runs stale code. Every tool checks the server's own loaded source files and fails with "reconnect with /mcp" once any has changed on disk. Every bridge call checks the Blender-side source files: when they have changed and the open file is saved, Blender restarts on the new code and reopens the file; with unsaved changes, only `saveFile`, `newFile`, `openFile`, and status calls run until the work is saved or discarded. Renders rebuild their preview scene each time, so they always reflect the current scene.

| Tool | Does |
|---|---|
| `runPython` | Fallback only: runs code in a persistent namespace (`bpy`, `bmesh`, `mathutils`, `math`) and returns printed output and `result` if the code sets it. Every call is logged to `logs\runPython.<date>.log`; `getToolingStatus` counts them |
| `newFile` / `openFile` | Start an empty scene or open a .blend by absolute path; refused while the open file has unsaved changes unless `discardUnsavedChanges`; opening makes each water material's reflection lookup again from its cube map where this machine's tooling root lacks it (`environmentLookupsMade`) and lists water whose cube map file is missing (`environmentMapsMissing`) |
| `saveFile` | Saves, or saves as an absolute path; textures and linked libraries become paths relative to the .blend; packed, generated, missing, or other-drive images are refused |
| `saveCheckpoint` | Saves the open work file, then copies it to a recovery point under the tooling root, `checkpoints\<work file name>-<hash of its full path>\<UTC time>_<label>.blend`, never beside the work file; refuses a scene never saved or one `saveFile` refuses |
| `listCheckpoints` | The open work file's checkpoints, or those of the work file at a path: name, label, UTC time, size, and their total size |
| `restoreCheckpoint` | Keeps the current state as a checkpoint labelled `before restore <time of the checkpoint restored>` (restoring that takes the restore back), copies the checkpoint over its work file, and reopens it; refuses a checkpoint of another work file than the open one, since a work file's textures are on paths relative to it |
| `deleteCheckpoints` | Deletes the named checkpoints, refusing (and deleting none) when a name is unknown; a work file's folder goes with its last checkpoint; nothing else deletes a checkpoint |

fog color, start, end, and density; `fogOn` (the zone row's ztype is not 0) and `minClip`/`maxClip` (the zone row's clip distances; previews clip at the maximum and pull a fog end that reaches it in, as the client does); `newEngineZone` (the zone header's `NewEngineZone`, which sets the scale spawns draw at); and `sky` {type, weather, hour, minute}, the client sky the zone draws, which supplies the ambient, bounce, sun color and direction, and fog color in place of hand-set ones and reports how the client resolves it, or `sky` "none", stating that the zone draws no sky (its zone row's sky 0), so the fog color shows where nothing is drawn and the light is set by hand; `safePoint` [x, y, z, headingDegrees], where players arrive, and `underworld`, the height below it under which the client puts a falling player back; and the zone's server row, which a game export needs whole and each value of which is checked when set: `shortName`, the zone's short name (1 to 31 lowercase letters and digits), which names its files and rows and by which a zone line leading back into the zone is told from one leading out, and `zoneId`, its id as the server sends it (1 to 999 but 997, the client's run-time zone), by which the client also caps the reach of carried lights, neither one the client registers to another zone (an id it does not register and a short name it does are findings of an export: see Server files), and an id the client does not register a new zone's, above 786 (787 to 999 but 997), as EQEmu's new-zone process gives it: a new zone takes its own id and short name, never an existing slot (`checkServerZoneSlot` reads the servers); `eqstrID`, for a new zone, the id of the client string (`eqstr_us.txt`) holding its long name, which the client's entry names, refused when the client's `eqstr_us.txt` holds another string under it; `longName`, the name players see (1 to 127 printable ASCII characters); `timeType` (the row's `time_type`: `indoorDungeon`, `outdoor`, `outdoorCity`, `dungeonCity`, `indoorCity`, or `outdoorDungeon`); `entryGate`, who may enter: `"open"`, `{"minStatus": n}` (an account status, 0-255), or `{"zoneFlag": true}` (a character needs the zone flag for this zone's id; ### Artist toolkit

Edits address parts of a mesh with selectors instead of an interactive selection: `{"all": true}`, `{"sphere": {center, radius}}`, `{"box": {minimum, maximum}}`, `{"cylinder": {center: [x, y], radius, bottom, top}}`, `{"facing": {direction, withinDegrees}}`, `{"slope": {minimumDegrees, maximumDegrees}}` (0 flat, 90 vertical, over 90 overhanging), `{"height": {minimum, maximum}}`, `{"nearPath": {path, radius}}`, `{"material": name}`, `{"vertexGroup": name}`, `{"insideObject": closedMeshName}`, `{"region": regionName}`, `{"noise": {featureSize, share, seed}}` (patches of smooth noise covering about `share` of the surface, for breaking up one material with another), `{"underWater": waterBody}` (a pool or river's bed: faces whose every corner lies under its surface or on it), `{"nearWater": {water, distance}}` (wet banks: faces out of the water that the waterline crosses or meets, so bed and banks leave no gap, or all of whose corners lie within `distance` of it in plan), `{"cave": caveName}` or `{"cave": true}` (the lining of a cave `cutCave` made, or of every cave), and `{"and": [...]}`, `{"or": [...]}`, `{"not": selector}`. Shapes test vertex positions in world units, or face centers for face operations. The water selectors follow whole faces, so a bed and a bank band end exactly on the waterline and `distance` out from it only where the mesh is cut along those lines (`cutContours` with `waterline` and levels `[0, distance]`, for a pool or a sloping river; `carveWaterBed` cuts the waterline itself). A selector that matches nothing is an error.

Every tool that looks for the ground players stand on (`standAt` and `figureAt` views, `measure`, spot heights and `sketch` measurements, `renderSection`'s ground, placing, scattering, and settling, plots and their grading, water's ground, and `walkRoute`, which also meets the boundaries) takes it by one rule: rendered meshes and collection instances, but not water bodies, guides, regions, spawns, or doors, and never what players pass through: objects marked passable, faces of cutout and liquid materials (which export flags 0x1), and the faces an imported EQG zone flags 0x1. The client collides with the cutout faces its file leaves unflagged (Dranik's Scar's palm fronds), so players stand on them here too; classic zones and client models placed by `placeObject` come in without their files' flags, so their cutout faces are ground. Where an imported zone lets players through its water or lava surface, they swim under it, as under a pool; where nothing lies under such a surface there is no ground, so a view standing there is refused and a spot height left out. A surface named to place or settle on (`surfaceObjects`, `onto`) is taken whole.

## EverQuest reference

`zonewrightEverQuestClient` points at an EverQuest client install. The `zone-survey` skill (`.claude/skills/zone-survey`) describes how to answer zone questions from the survey, and holds the procedure for interpreting a zone, with its version and zone types, which the server reads from it. Scale and layout come only from the actual zone files: classic WLD (`.s3d`), EQGZ (`.zon` with `.ter`/`.mod` models, including archives named in `<zone>_assets.txt`), and EQTZP terrain (`.zon`/`.dat`). Brewall map files (`maps\Brewall`) are not authoritative geometry; they serve only as place names for design notes.

### Server files

An EQEmu server loads a collision map (`.map`), a region map (`.wtr`), and a nav mesh (`.nav`) for each zone. `server/serverMapFiles.py` writes the `.map` and `.wtr` from a zone archive's own files, as azone and awater would and as the server reads them, refusing what either would drop, and reads all three to their last byte; `mapCollision` rebuilds the triangles the server collides with from a `.map`, and `server/serverMapDrawing.py` draws them in plan with the `.wtr` boxes, and draws the server's view of a zone (`drawServerPlan`, below). From the client's files they reproduce Peridot's Highpass Hold, thulehouse2, and Freeport maps byte for byte but for azone's rounding of placement turns, and their `.wtr` files exactly with the regions unturned, as Peridot's awater wrote them. Formats, frames, rules, and the evidence are in [docs/serverFiles.md](docs/serverFiles.md). A game export writes all three from its archive's bytes (see Export).

The server also needs the zone's rows: a `zone` row and a `zone_points` row per zone line. zonewright never connects to a database. `server/serverRows.py` writes them as SQL files the owner applies with the `mariadb` client, each one compound statement holding its transaction, whose guards `SIGNAL` naming what they found and whose every write is undone by a guard's `SIGNAL` or a failed write, however the file is applied: `<short>.sql` upserts the zone row (a new row copies every column zonewright does not write from `serverTemplate`'s version-0 row; an update never changes `zoneidnumber`) and replaces the `zone_points` rows of the zone's own zone lines, deleting only rows an export of this short name wrote, where the table still holds them as written, and refusing a number it writes where any other row stands (a version -1 row there too, which the server loads into every version of the zone), so a reused slot's other rows stay; `<short>_waysIn.sql` points each neighbour row a `zoneIn` entry names (`fromNumber`) at a player's height over the entry, guarded to exactly one version-0 row with no version -1 row beside it. A strict reader reads both back. The zones the client registers come from its own `eqgame.exe`, read in place (`server/eqClientZones.py`): a client loads a zone's files only by an id it registered, so setZoneProperties refuses an id or short name it registers to another zone, placeZoneLine and placeEntry a target or `fromZone` it does not register (the zone's own short name aside), and an export lists an id it does not register (it needs a registration entry before the client can load the zone) and a short name it does (a reused slot: the export replaces that zone's server maps and rows, which every instance of it uses). A game export writes both files under `server\sql` (see Export). A zone the client does not register needs the client's entry before a client loads it; a game export of one needs `eqstrID` and gives the entry in its manifest and result (`clientEntry`, `server/eqClientZones.py`), by EQEmu's documented route for now (eqemu-docs-v2 `client/guides/custom-zone-editing.md`): eq-core-dll's `ZoneEntry(zoneType, zoneID, short name, long name, eqStrID, zoneFlags2, 0, 0, 0)` line, its zoneType and zoneFlags2 the template's own registration, and the `eqstr_us.txt` line `<eqStrID> <long name>`, with string 0's count one higher where the line is new (string 0 holds how many strings follow it: 7135 in the RoF2 client). zonewright's own client tools replace that route later. The format, columns, and guards are in [docs/serverFiles.md](docs/serverFiles.md#zone-row-and-zone-points).

### Export

`exportZone` and `checkExport` take a required `purpose`. A `test` export is for quick renders and test loads: it writes everything designed and requires nothing beyond the hard errors, listing what a game export would still refuse as findings. A `game` export is for the EQ client and server and also requires completeness. There is no skip flag.

Both take `path`, an absolute `<short>.eqg` in an existing folder, the short name lowercase letters and digits and at most 31 of them, and refuse an export that would write or remove any file inside `zonewrightEverQuestClient` (which must hold `eqgame.exe`), however its path is spelled: each folder holding a file the export touches, resolved through links and junctions (a `server` folder linked into the client among them) and `..`, is compared with the client folder by file identity, so case, short names, and extended-length and UNC loopback prefixes all count. An export writes and removes files beside its archive and would remove the client's own, such as `neighborhood_assets.txt`. An export goes to a staging folder, laid out as:

```
<folder>\<short>.eqg                      the archive, with _EnvironmentEmitters.txt, _assets.txt and _housing.json as the zone needs them
<folder>\<short>_export.json              the manifest
<folder>\server\maps\base\<short>.map     game only, as the three below
<folder>\server\maps\water\<short>.wtr
<folder>\server\maps\nav\<short>.nav
<folder>\server\sql\<short>.sql             the zone row and its zone_points rows
<folder>\server\sql\<short>_waysIn.sql      only when a zoneIn entry names its neighbour's row
<folder>\server\sql\<short>_pieces.sql       the interactive pieces' doors and object rows, when the zone has any
```

`server\maps` mirrors the server's own `maps` folder, so it is copied whole; every map is named by the lowercase short name, as the nav loader does not lowercase. `server\sql` holds what the owner applies with the `mariadb` client (Server files above). The manifest records the purpose, the tool that wrote it (`writtenBy`: `exportZone`, or `checkExport` for a check's files), the short name, the `.blend`, every file written with its size and SHA-256, and the failure and finding counts; a game export's also records the zone's short name, id, long name, template, and `eqstrID`, the client's entry for a zone the client does not register (`clientEntry`, Server files above), the `zone_points` numbers written and deleted, `serverNavSettings`, the Recast helper's commit and fingerprint, the nav's main piece, every island with whether players reach it, and the path probes, and the lane's key, grid, constants with their sources, and reached area. Before anything is written, what could not be put back refuses: a target that is a folder or read-only (Windows renames a read-only file but will not remove it), a file where a folder must be, and a `<file>.previous` an export that did not finish left, which may hold its only copy of the last export's file. Then every file is written whole under a temporary name, the last export's files are taken aside as `<file>.previous`, the others are put in place and the archive last; a failure before the archive is in place puts every file back as it was and names any step of that which failed, and once the archive is in place the files taken aside are removed (one that cannot be is a failure saying the export is in place).

`server/exportPipeline.py` runs both purposes. A test export writes the archive, its side files, and the manifest, and removes this zone's files under `server\`, which would no longer match its archive, listing them (`serverFilesRemoved`). A game export, once the checks find no hard error, also builds the server's side, in order: the `.map` and `.wtr` from the archive's bytes, then the `.nav` (the Recast helper must be built: a game check or export refuses with "run syncTooling" otherwise), inspected as the server loads it for NPC islands and paths probed from the safe point to each zone line, stored entry, and plot entrance (an entry or plot entrance reached only when the server's goal for it, the nearest polygon its ground filter allows, lies within the NPC's radius and climb of it: a landing on a tower whose top holds no nav is not, as NPCs path only to its foot); the player's lane, the one `mapReach` computes and reuses, judged for containment, each island flagged where players reach it (some reached floor within a step of one of its polygons); the ground under the safe point, every stored entry, and every zone line's landing back in the zone, found as the server's FindBestZ finds it on the `.map` (straight down from 1 over the point, the first collision met at or above the underworld); and the rows, once the zone row's values are set and the archive is named by the short name. A nav the helper refuses is a failure; islands and probe failures are findings. Containment's failures are the lane's leaks (a fall onto nothing, a move under the underworld, reach into a `none` region or outside every region), an entry the safe point and it do not reach both ways unless it is isolated, and a plot entrance no player reaches, each with its place and `mapReach`'s number for it; without a safe point or a stored entry the lane has no seeds, and that is a failure ("containment not checked: no seeds"), never a skip. The lane's other problems, squeeze reach, a zone line overlapping a swim box (the `.wtr` lists swim boxes first, so the server reads the overlap as water), no zone lines, no `zoneIn` entry, and what the lane does not model and its limits are findings. `zone_points` rows are known as zonewright's by the record under the tooling root (`%LOCALAPPDATA%\zonewright\exports\<short>\zonePointsWritten.json`), which holds every row any game export of the short name wrote, whole: a game export adds its rows to it before writing its files (a row recorded and never applied only makes a later delete match nothing), so a later export deletes a removed line's row wherever it is written; a check never changes it. `checkExport` with `game` writes nothing at `path` but builds every file of a game export into `%LOCALAPPDATA%\zonewright\exports\<short>\check\`, replacing the last check's (its manifest says `checkExport` wrote it, so `verifyExport` refuses it: a check is no export), and its `serverFiles` gives where they went, the nav's inspection (the 25 largest islands; the manifest has every one), and the rows (numbers written and deleted, ways in to add on the server), and its `containment` the lane it judged; when the checks found a hard error it says "server files not built" and names them. `serverMapDrawing.drawServerPlan` draws the server's view from those files alone: the `.map`'s collision in grey relief, what of it stands upright (walls, the sides of blocks, which the relief cannot show from above) as dark red lines, faces steeper than the NPC nav walks (`maxSlope`) hatched brown, and what it never collides with in blue, the `.wtr` boxes in their types' colors, the NPC nav's main piece green and its islands orange and numbered (lavender where players do not reach them, by the export's flags; an island lying under a higher one, such as a closed block's hollow inside, outlined dashed and numbered "N (under M)"), Disabled and zone-line polygons dark, and marked points such as the safe point, with the scale bar under the plan and a legend naming each mark and the axes.

- **Hard errors (both purposes):** unsaved changes (an export writes the zone as saved); objects export cannot take (a non-mesh in the terrain collection, or among a placed collection's members, to any depth, anything but meshes and collection instances, such as a plain empty or a light; a model scaled unevenly; model names that collide once lowercased, a kit's collection among them; a placed model of more triangles than the client draws, 3,600); a placed kit piece or building, or a structure, whose kit file is gone or no longer holds what it placed; two materials that would share one name in the archive (two kit files of one name holding materials of one name); faces with no material or a material `createMaterial` or `createLiquidMaterial` did not make; a missing, packed, generated, or other-drive image, a non-DDS image whose sides are not powers of two, DDS data under another extension, two images that would share one DDS name; meshes without texture coordinates; a liquid material on anything but a water body; a mesh with surfacing layers whose modifiers change its faces; swim volumes a zone file cannot hold; boundaries that are not meshes or have no faces; zone lines a zone file cannot hold (a name the client reads no number from, a turned box, a box without size, region names that clash once lowercased); housing the server would refuse; caves broken by a change outside their guards (an edge on three or more faces or an open edge at a mouth, a plug id lost or carried twice, a ring vertex off its plug triangle or a lining vertex moved in some pass).
- **Game only, listed as findings by a test export:** blockout materials on exported faces; caves and defined passes whose ground moved since they were made (stale: listed under `toConfirm` by a test export, to refit with `regradeTerrain` or `editCave`); structures laid on ground, a wall, or a kit that has changed since (stale, listed under `toConfirm` with why: `editStructure` lays them again); every pool and river decided for swimming (no undecided or changed bodies); the zone row's view values (`fogOn`, `minClip`, `maxClip`, `sky` or `sky` "none" stated for a zone that draws none, and the fog's start, end, and density when it is on, and its color when the zone draws no sky); its identity, gate, and template (`shortName`, `zoneId`, `longName`, `timeType`, `entryGate`, `serverTemplate`), the archive named by the short name, and a stored sky the game draws (the client picks its sky by the short name, as EQEmu sends no override, so a sky type resolving to another sky setting than the short name's previews a sky the game never draws; both resolving to `default` is fine); every zone line leading to a zone the client registers or back into this one; the safe point and underworld, with ground the zone ships under the safe point above the underworld (an imported reference zone under it is no ground); a target for every zone line and each number used once; the player space decided: regions at all, every region's access, and every stored entry on its footing; a nav mesh the Recast helper builds (its refusal is listed with why; a test export builds none); and what the server side shows, which a test export never builds: containment on the lane, the ground the server finds under where players arrive, and rows that can be written.
- **Collision as written:** the boundaries (`placeBoundaryWall`, `placeBoundaryPlane`) merge into the terrain's `.ter` as triangles with material -1, which the client never draws (its draw batches skip them) and still collides with, flag 0. A wall goes in twice, facing each way: the client's own walls are single triangles facing the play area (Highpass Hold's, and over 99% of the upright ones across its EQG zones), whether its collision lets a player through a wall's back is untraced, and a wall here faces left of its path, which on an open path can be away from the play area. A lid faces down and a floor up, as the client's lids face the play area; liquid surfaces, cutout cards, and objects marked passable are flagged 0x1, which the client's collision tests skip; zone lines become unturned `ATP_<number>_<label>` regions. A game export writes their `zone_points` rows, and the zone row with the safe point and the underworld, under `server\sql`.
- **Structures as written:** a kit piece placed by hand is one model (`obj_<piece>.mod`) however often it is placed, turned about Z at each placement; a placed building is one model per part (`obj_<prefab><part>.mod`, its nested pieces merged about the building's origin) shared by every placement of it, and its plinth one model of its own; a bridge, flight, or walkway is one model (`obj_<name>.mod`), or, laid in the `terrain` collection, terrain triangles in the `.ter`; a wall places its section piece's model where it stands level, one `obj_<piece>up<r>.mod` or `down<r>` per distinct shear shared by every wall in the file, and its post's model at each post; a carved hall and its facade are terrain. A span's rope and rail faces are flagged 0x1 by their face flag as a rope's cutout material flags it. Materials are told apart by their full names, so a kit's material and the zone's own of one name both export, the kit's as `<name>_<kit file stem>`. The report gives each structure's models with their triangles and placements, its triangles in all, and `placedTriangles`, which `compareWithClientZones` sets beside the client's zones.
- **Findings about the zone's slot, never refusals, for either purpose:** an id the client does not register (the client needs a registration entry before it can load the zone), and a short name it does register (a reused slot: the export replaces that zone's server maps and rows, which every instance of it uses).
- **Findings (texture coverage), never refusals:** the base material showing where no unmuted surfacing layer covers a face; ground borders on the terrain where two ground materials meet, ground no steeper than 60 degrees on at least one side, with no `paintTransition` strip between them, as a length per pair of materials and its stretches (each a center, bounds, and length); texture stretched or squeezed, where a texel lies over twice as long one way as the other in the world or a face's world units per repeat are over twice off, either way, its material's area-weighted median; zero texture area; and back faces, faces wound against the rest of their surface (a closed surface faces out, a terrain sheet up, any other sheet the way most of it faces). The checks never assign a material, texture, or texture coordinate, and there is no fallback texture.

Each failure and finding names the object (and, for a collection's mesh, the instances that place it), the material, the image (a packed or generated one by its file or its image name), and the face count, with the faces' connected pieces, largest first (center and face count); a swim volume, boundary, or zone line a zone file cannot hold is named with where it stands. `renderView` with shading `coverage` draws the same statuses, so a list and a picture of it can be checked against each other.

#### Verifying an export

`verifyExport` (`server/exportVerification.py`) reads a game export back from its folder, after `exportZone` wrote it, and judges it against the open, saved scene and against itself; it writes nothing beside the export (its renders and pictures go under the tooling root). Every check runs whatever the others find, each `{check, passed, details}` with its failures and where each lies, and `failedChecks` names those that failed:

1. **manifest:** every file the manifest lists lies in place with its size and SHA-256, every file a game export writes is listed (the archive, `.map`, `.wtr`, `.nav`, and `<short>.sql`), nothing of the zone's lies beside it unlisted, and the server files are named by the lowercase short name, each lying under its exact name as the folders spell it (`os.scandir`: Windows finds a file whatever its case, where the server on Linux opens only the exact name).
2. **current:** the archive the saved scene makes now, built in memory as a game export builds it, equals the exported one entry by entry; the entries that differ are named (the scene changed since this export).
3. **archive:** every entry reads with its kind's reader (`.zon`, `.mod`, `.ter`, `.dds`, `.lit`), every placement's model is in the archive, and the `.zon`'s regions are the swim boxes and then the zone lines as the scene holds them (names, centers, half extents).
4. **map:** the `.map` inflates to its stated size and reads to its last byte, every placement names a model it holds, it equals the `.map` the archive makes, and the collision the server rebuilds from it is the archive's solid triangles as the client places them, in count and order, every corner within 3.2e-4 (Peridot's Highpass Hold `.map` lies that far from the client's placing along the server's float32 path).
5. **water:** the `.wtr` as the server reads it (magic, version 2, its exact length: a file cut short is one the server logs as "Loaded Water Map" and drops, turning NPC nav pathing off), and equal to the `.wtr` the `.zon`'s regions make.
6. **nav:** the container inflates; its parameters are `serverNavSettings` over the `.map`'s collidable extents; the pinned helper rebuilt on this `.map` and `.wtr` reproduces its payload byte for byte; Detour loads every tile as the server loads them; and its water, lava, and Disabled polygons lie in the `.wtr` boxes that mark them (a corner within a nav cell of the box across and the NPC's climb over it).
7. **rows:** zonewright's reader reads `<short>.sql` and `<short>_waysIn.sql`; the zone row's written columns are what the stored inputs make, and its template is `serverTemplate`; every guard is there with its values; there is one `zone_points` row per zone line, numbered ten times its number, at a point inside its box, and every column it writes is what `serverRows.zonePointRows` makes of the scene's line (its place, target and heading, the client's target id, and the rest); and the ways-in file holds exactly the `zoneIn` entries naming a neighbour's row.
8. **ground:** the ground the server finds on the `.map` (straight down from 1 over the point, at or above the underworld, as the zone row holds both) under the zone row's safe point, every stored entry, and every `zone_points` landing back in the zone; and under a landing in another zone, the ground on that zone's client collision (its solid surfaces and invisible walls), where a miss is a finding, that zone's underworld being unknown here.
9. **clientModels:** the zone stands alone: every `.zon` placement and every row names a model the archive holds, every texture its models' drawn materials name is in the archive or registered at startup (one the manifest records missing for the client too aside), every client model the manifest records is in the archive byte for byte under the name it was stored under (one naming a texture stored under another name, the client's with only those names changed) and the client's own entry is unchanged, no interactive piece is also a `.zon` placement at its place, and every object row stands where FindBestZ puts it on the exported `.map`.
10. **containment:** the lane the server files give (`playerReach.laneFromServerFiles`, seeded where the scene's entries stand, with its regions, plot entrances, and underworld) holds no leak a game export refuses; its reached area is given beside the manifest's.
11. **looks:** every review camera and the lane tour's eyes (`viewFromLane`'s tour, kept beside the lane, chosen and kept if none is) are read as poses first, with where each stood the scale figure; each is rendered in client shading in the work file with everything export leaves out (`classifyObjects`' excluded list: reference zones, placed client spawns, the doors and objects `placeDump` placed, guides, and their lights and emitters) left out of that render only, then in a new file holding the archive brought in by `importZoneFile` with the zone's view values, from the same pose; then the saved work file is opened again, also when the call is cancelled, and an archive that does not import or draw is a failure naming why. A view is alike when the mean difference of its pixels' channels is under `buildTolerances.roundTripMeanLevels` (0.5 of 255), the 99th percentile of each pixel's largest channel difference at most `roundTripPercentileLevels` (2), and under `roundTripChangedShare` (0.1%) of its pixels have a channel more than `roundTripChangedLevels` (8) off, so a model missing or a texture changed over a small part of the view fails where the mean and the percentile would let it pass.

The server's view is `serverMapDrawing.drawServerPlan` on the exported files alone: the `.map`'s collision, its `.wtr` boxes labelled with the archive's regions and the `zone_points` rows standing in them, the `.nav`'s main piece and islands (each island's players' reach as the manifest records it), and the safe point, `zone_points` positions, landings back in the zone, and ways in that the rows name; without a `.nav` it draws none and says so. The comparison sheet sets each view's scene render, archive render, and difference (the scene dimmed, red where the archive's differs, full at twice the percentile tolerance) in a row, the views that draw otherwise first and each group by its mean difference: every view that draws otherwise and the others up to five rows, five rows to a sheet, each sheet captioned "N of M views shown" with when a view draws alike; every view's numbers and its three files are in the JSON.

#### Client models in a zone

A client model a scene places with `placeObject` or `placeDoor` ships with the zone, as the client's own zones share models: `exportZone` copies its entry and every texture its drawn materials name into the zone's archive byte for byte, once each, taken from the archives the client loads it with (its own first), and records each copy's archive, entry, size, and SHA-256 in the manifest (`clientModels`) (`server/clientModelBundle.py`). A copied texture whose name the archive already holds with other bytes (ours, or another copy's) is stored under its archive's name before its own (crescent.eqg's `av_wood01a_c.dds` as `crescent_av_wood01a_c.dds`), and each copied model naming it names that instead, its other bytes the client's (the manifest records the copy's `renamedTextures` and `storedSha256`). A copied scenery model whose entry name the archive already holds with other bytes (ours, another copy's, or the same model drawn with other textures, as Buried Sea's and the Commonlands' `obj_druid_ring_a.mod` are) is stored the same way (mesa.eqg's `obj_takruins_medrockb.mod` as `mesa_obj_takruins_medrockb.mod`; the manifest records the copy's `storedEntry`), and the `.zon` places that file: an EQG placement names its model by the `.zon`'s list of file names, and the client registers each as that name less its extension plus `_ACTORDEF`; nothing inside a `.mod` names it. The same model with the same textures, placed again or from another archive, keeps one copy. Interactive pieces claim their names first, since their rows name the model by entry. A `.zon` resolves a placement's name only against the zone's own archive and the startup archives while the archive loads, so nothing static depends on `<zone>_assets.txt`.

- **Scenery** (`placeObject` by default, `placeDoor` with `interactive` false) is a `.zon` placement under the client's entry name or the name it is stored under (`OBJ_FSCRYSTALA01` places `obj_fscrystala.mod`, `MESA_OBJ_TAKRUINS_MEDROCKB01` places `mesa_obj_takruins_medrockb.mod`), turned and scaled as placed.
- **Interactive pieces** are what EQ makes server-side, exactly what its `doors` and `object` tables hold: a door's open type, destination, key, lock, and trigger; an object's type (a tradeskill container's kind, or a plain clickable object). Each is a row of `server\sql\<short>_pieces.sql` (`server/pieceRows.py`) naming the copy in the archive (a door its bare name, an object `<NAME>_ACTORDEF`), never also a `.zon` placement. Doors are numbered 1 up in object-name order (the client's door id is one byte); a number written where another row stands refuses unless an export of this short name wrote that row, and object rows, whose id spans every zone, replace by value the rows earlier exports wrote, both kept in `exports\<short>\piecesWritten.json` under the tooling root. The server stands every object row on its `.map` as it boots (FindBestZ), so a game export refuses one it would move (a test export lists it).
- **Client meshes are not edited:** a placed spawn, door, or object (and its mesh, whose mark copies keep) is placed, moved, turned, and scaled; every mesh-editing tool and `booleanCut`'s cutter refuse it.
- **Refused:** a classic actor (a WLD no EQG archive holds), a skinned model (its animations are not copied), a client entry patched since it was placed, an interactive piece whose model's entry name the archive holds with other bytes (ours or another row's: its row names the model by that name, so its copy is not renamed), a copied model clashing under its stored name too, a copied texture clashing under a name the startup archives register (the client draws that one whatever the archive holds) or under its stored name too, our texture under a name a startup model registers with other bytes (the client draws the startup one on our faces), a client model's copy shipping as one of our meshes or inside a placed collection, a scaled-unevenly piece, an interactive piece turned about anything but Z or scaled past what its row holds, a door triggering no interactive door, and a piece placed both as scenery and as a row. A texture no archive the client loads the model with holds is missing for the client too and is listed; a copied texture a startup material registers with other bytes is listed (the client draws the startup one there too); the bytes the copies add are listed, with no budget until Phase 2 measures a real zone.
- **Reference content:** what `placeDump` places (the client's own scene, for calibration) is left out of exports.
- **Back in:** `importZoneFile` places a game export's rows beside its archive in `<zone> rows`, each model drawn from the archive alone and each object where the server stands it.

#### Handing off

The `prepare-export` skill (`.claude/skills/prepare-export`) takes a zone from a settled design to a verified game export and ends in a hand-off note, every step judged in the picture it names. A game export is staged under the tooling root (`%LOCALAPPDATA%\zonewright\staging\<short>\<short>.eqg`), never in the client folder or the work repository. It is deployed first on claudeperidot, Claude's own test EQEmu server, with `deployZone`, through its change ledger (`claudeperidot/`; Deploying, below). Peridot is the owner's server: the owner applies the export there from the note, which lists every file with its SHA-256 from the manifest and where each goes:

| File | Goes to |
|---|---|
| `<short>.eqg`, `<short>_EnvironmentEmitters.txt`, `<short>_assets.txt` | Every player's client folder |
| `server\maps` | The server's own `maps` folder, copied whole (`base`, `water`, `nav`) |
| `server\sql\<short>.sql` | Applied with the `mariadb` client; world reads the zone table when it boots and a zone process loads its maps and zone points when it boots, so world and the zone processes restart after it |
| `server\sql\<short>_waysIn.sql` | Applied only if the neighbours' rows are to change, since it rewrites another zone's `zone_points` rows |
| `server\sql\<short>_pieces.sql` | Applied with the `mariadb` client; a zone process loads its doors and objects when it boots |
| `<short>_housing.json` | The server's plot content, never a client folder |
| `<short>_export.json` | Neither: the manifest the note's hashes come from |

The note also gives the entry gate (for a zone flag, that each character needs it granted), the template the new zone row copies, the ways in to add on the server for `zoneIn` entries without a neighbour row (`waysInToAdd`), the client's entry for a zone it does not register (the manifest's `clientEntry`), that a reused slot's server maps and rows are replaced for every instance of it, and each finding accepted with its reason. Claude never applies anything to Peridot and never copies into a client folder.

#### Deploying

A zone's server side reaches Claude's test server only through `deployZone`, and only through the claudeperidot ledger (`claudeperidot/README.md`), whose `tools/zoneDeploy.py` zonewright runs with the ledger's own interpreter (`python` with PyYAML and facet's client, as the ledger needs them): zonewright builds the request from the export as written (`server/zoneDeployment.py`) and reaches no server itself. Only a new zone deploys, with an id and short name the client does not register, the id 787 to 999 but 997, and no other zone's row holding either on the server. `zoneDeploy` writes two changes, `<UTC YYYYMMDD-HHMMSS>-deploy<Short>Maps` and, a second later, `-deploy<Short>Rows`, adds them to the plan step the caller names, commits and pushes them, then stages and applies each with the ledger, so each is recorded before it runs and reverts:

| Change | Kind | Scope | Apply |
|---|---|---|---|
| `deploy<Short>Maps` | `files` | `/opt/eqemu/akk-stack/server/maps/{base,water,nav}/<short>.{map,wtr,nav}` | Each installed from the export's `server\maps`, owned as its folder is, mode 644; stage keeps any file it replaces on the host for revert |
| `deploy<Short>Rows` | `db` | `zone` `short_name = '<short>'`, `zone_points` and `doors` `zone = '<short>'`, `object` `zoneid = <id>` | Each table's rows of the zone deleted and the export's inserted (the zone row copying every column the export does not write from the template's version-0 row); `check.sql` gives 1 only when the zone's rows are exactly the export's |

A part the server already holds as exported is left alone; an earlier deploy of the zone still applied is reverted first and taken off the plan, so each part has one applied deploy, whose saved state is what was there before the zone's first deploy. Then EQEmu restarts with Spire's launcher in the server container (`eqemu-server:launcher stop`, until no world or zone process is left, then `start` detached, until world and a zone process run), as world reads the zone table and a zone process its maps, zone points, doors, and objects only when it boots. The ways-in file (it rewrites neighbours' rows) and the housing file (no server reads plot content yet: claudeperidot's database holds no housing tables) are left out and listed. `undeployZone` reverts the zone's applied deploys, newest first, and restarts.

The client side follows EQEmu's documented route for now, improvised as a proof of concept: the export's `clientEntry` (the `ZoneEntry` line for eq-core-dll's `_options.h`, with `areCustomZonesEnabled`, built into the spare client's `dinput8.dll`, and the `eqstr_us.txt` line) and the `.eqg` with its side files go into the spare client's folder (`S:\Research\EverQuest\housingclient`) as ledger client changes. zonewright's own client tools replace that route later.

### Client models

Spawns, doors, objects, and the scale figure come from the client's own models and animations, found the way the client finds them: only in archives the client loads in the zone, never by matching a name in an unrelated archive. The client keeps the first definition of any name it registers (`EQGraphicsDX9.dll` skips a name already present), so the order in which it loads archives decides between archives that define the same name. `findModel` shows the whole search for one model. The order, read from `eqgame.exe`:

1. **At startup** (`0x491c20`):
   - `Resources\GlobalLoad.txt` phases 1 and 2.
   - The Luclin player models, `global<code>_chr2` then `global<code>_chr`, for races 1-12, 128, and 130, male then female, when `eqclient.ini` turns that race's Luclin model on. The human and wood elf models also load when a race that borrows their animations (erudite; dark, half, and high elf) has its Luclin model on.
   - `Global5_chr2`, `Global5_chr`, and `frog_mount_chr` while `UseLuclinElementals` is on.
   - The Luclin equipment (`LGEquip_amr2`, `LGEquip_amr`, `LGEquip2`, `LGEquip`) once any Luclin model loaded.
   - `VEquip` with the Luclin Vah Shir, or `GEquip6` and `Global7_chr` unless both Vah Shir settings are on.
   - `GlobalLoad.txt` phases 3 and 4.
   - `Resources\GlobalLoad_chr.txt`.
2. **On entering the zone** (`0x49b200`):
   - `<zone>_pre_chr.txt`, and `poknowledge_obj3.eqg` for the Plane of Knowledge only.
   - For classic zones, `<zone>_obj2`, `<zone>_obj`, the zone, `<zone>_2_obj`, `<zone>_chr2`, `<zone>2_chr` (only for the zones `eqgame.exe` names), and `<zone>_chr`.
   - `<zone>_chr.txt`. Each line is `code,source`: a source that starts with the code loads `source.eqg` (else `source.s3d`); any other source loads only that code's actor from `source.s3d`.
   - The `.eqg` archives in `<zone>_assets.txt`, and, for EQG zones, the zone `.eqg`.
3. **When first needed:** `Resources\OnDemandResources.txt` EQG models (`EQGM`) and skinned models (`EQGS`).

The first definition in that order wins: IT67 is in both `equipment-01.eqg` and `gequip.s3d`, and the client uses `equipment-01.eqg`, which `GlobalLoad.txt` loads first. `source` picks a definition by archive instead. Of two `OnDemandResources.txt` lines naming one resource, the first registers: `EQGraphicsDX9.dll` skips a name already registered with the same type (`0x100c74f0`). One archive defining a model twice is an error, since which entry the client takes is not known. Textures come from the model's own archive or, for a zone's EQG model, from the zone's other EQG archives. A texture none of them holds is missing for the client too: its effect samples no texture there, which Direct3D 9 reads as black, so its faces draw black, lit and fogged, and every placement lists it in `missingTextures`.

Supported models:

- EQG models (`.mod`): static, or skinned when the file stores bones (Drakkin and many later creatures).
- EQG skinned piece models (`.mds`).
- WLD static actors.
- WLD textures: WLD meshes count `v` down from a texture's top row, so their UVs are flipped for Blender. Before this flip, faces drew upside down.
- WLD skeletal actors: skinned meshes and bone-attached meshes. Particle clouds are counted, not drawn.

Characters take the client's appearance rules (from `EQGraphicsDX9.dll`):

- **Pieces:** the body piece `<code><nn>` for `variation` and the head piece `<code>HE<nn>` for `headType`, keeping the default when the model lacks the piece.
- **Texture sets:** `.lay` layers `C_<code>_S<set>_M<n>` for `.mds` models, and `<code><part><set><nn>_MDF` materials for WLD ones.
- **Layers:** a layer's `M<n>` is entry `n - 1` of the model's material palette. A `.mds` palette holds every material (`0x100631e0`); a `.mod` palette holds only the materials its triangles use, in file order (`0x100620f0`), so an unused `FailsafeShader` takes no entry. A layer's textures are typed by the uppercase letter before `.DDS`: `C` diffuse, `N` normal, `E` environment (`0x100169cd`).
- **Blending:** an EQG material blends by the first family its shader's name contains (`0x100147f0`): `Alpha` blends by the texture's alpha and `Chroma` cuts out by it. `AddAlpha` (additive) is drawn opaque for now; see the [rendering worklist](docs/renderingWorklist.md).
- **Hair on other EQG models:** `hairStyle` attaches `<code>_HAIR_<nn>` (`eqgame.exe` `0x40ac80`, called for the head slot when no helm is worn) where the client defines one.
- **Attached EQG pieces:** a piece's first bone shares the matrix of the skeleton bone its slot names (`eqgame.exe` `0x40b580`: hair at `CHEST_CHEST03`, beard at `NECK_NECK`, facial attachment at `HEAD_HEAD`, tattoo at `ROOT_BONE`); each other bone shares the skeleton's bone of the same name (`0x10043e10`).

A Drakkin's look comes from `Resources\PlayerCustomization.txt`, as the client applies it to an EQG model of a player race when it spawns (`eqgame.exe` `0x40ecf0`; `eqLooks.py`):

- **The row:** the file has one row per race, heritage (`PARENT_ID`), and sex, giving a base color, a color list, and how many faces, hair styles, eye colors, beards, tattoos, and facial attachments there are (`0x8ce3f0`). A look past its count is 0; a heritage with no row is an error.
- **Face and eyes:** layers `C_<code>_HEAD_S<faceStyle>_M01`, `C_<code>_RIGHTEYE_S<eyeColor1>_M02`, and `C_<code>_LEFTEYE_S<eyeColor1>_M03` go on palette entries 0, 1, and 2 (`0x40ad60`, `0x40add0`). Both eyes take `eyeColor1`.
- **Pieces:** `<code>_HAIR_<hairStyle>`, `<code>_FACIALHAIR_<facialHair>`, `<code>_TATTOO_00`, and `<code>_FACIALATT_<details>` attach at their slots (`0x40ac80`, `0x40acf0`, `0x40ae60`, `0x40b050`). A tattoo past 0 lays `A_<code>_TATTOO_S<tattoo>_M01` on the tattoo piece. A piece no archive defines attaches nothing, as for `DKM_HAIR_08`, and is listed under `unattached`.
- **Color:** hair and facial hair take the color list's `hairColor` and `facialHairColor` entries; the tattoo and facial attachment take the base color. Black leaves a piece untinted (`0x40b260`).

A Luclin character's head follows the client's appearance rules (`eqLooks.py`, traced from the character customization window into `eqgame.exe`):

- **Face:** `faceStyle` swaps each head material `<code>HE000<part>_MDF` for `<code>HE<face / 10><face % 10><part>_MDF` where the file has it (`0x40d1a0`, the face split by `0x40c2a0`).
- **Hair and beard:** these are item models, not part of the body. Hair style `n` attaches `IT<1000 + block + n>` and beard style `n` attaches `IT<2000 + block + n>`. The block is per race, 30 higher for females (`0x40a290`); a human female's styles are `IT1390`-`IT1392`. They come from the Luclin equipment archives (`lgequip.s3d`, `lgequip2.s3d`, `vequip.s3d`).
- **Attachment points:** hair attaches at `<code>HAIR_POINT_DAG` and the beard at `<code>BEARD_POINT_DAG`, each item in its own bind pose. A point the skeleton lacks, or an item no loaded archive defines, attaches nothing, as in the client; placements list these under `unattached`.
- **Who gets none:** froglok and Vah Shir characters take none unless the face is 7 (`0x40aaa1`). High, dark, and half elf males and dwarf females take no beard (`0x40a240`). Style 255 is none.
- **Color:** `hairColor` and `facialHairColor` index the client's 24-color table (`0xac1a70`), which tints the item's grayscale texture (`0x40b260`). An index past the table leaves the item untinted.
- **Eyes:** both eyes take `eyeColor1` as the spawn appears (`0x40f032`). The DLL finds the eye entries in the model's material palette by name (`<code>L_EYE...`, `<code>R_EYE...`; `0x10040c50`). It swaps each for `CHR_EYE<color + race offset>_MDF`, looked up by name in what the client loads, which is `lgequip.s3d` for most races (`0x40c350`, `0x10040d50`). The offset is 20 for dark elves, 40 for iksar, 60 for Vah Shir, 80 for ogres, 100 for trolls, 120 for frogloks, and 0 otherwise. A human male's face 3 and a barbarian male's face 6 fix the right eye at 209; a dwarf male's face 5 and a barbarian male's face 4 fix it at 207. Color 255, or an eye material no archive defines (such as the dark elf's default `CHR_EYE020_MDF`), leaves the eye as modeled.

What characters and models do not yet draw as the client does (particle effects, additive blending, equipment) is in [docs/renderingWorklist.md](docs/renderingWorklist.md).

A WLD character plays the client's animations (`eqAnimations.py`, transcribed from `eqgame.exe`):

- **The animations:** the 78 the client loads per model (`C01`-`C11` combat, `D01`-`D05` damage, `L01`-`L12` movement, `O01`-`O03` idle, `P01`-`P09`, `S01`-`S29` social, `T01`-`T09`), with the client's own labels such as `WALK` and `WAVE`.
- **Borrowing:** a model without an animation borrows another code's (`0x406a60`): dark, high, and half elves the wood elf's, Luclin erudites the human's, kobolds the werewolf's, and about a hundred more rules. The model's own animation comes first (`0x407800`).
- **Variants:** a Luclin model (one with a `<code>TUNIC_POINT_DAG` bone) takes lettered variants such as `L01A` and `L01B`; it takes an unlettered animation only if it has at least 50 tracks.
- **Frames:** each frame decodes as the client does (`0x1001b190`): rotation, translation over 256, and a uniform scale over 256. Bones without a track in the animation keep their bind transform.
- **Duplicate tracks:** of two tracks with one name in a file, the first plays. `EQGraphicsDX9.dll` registers tracks in file order, and `d3dx9_30.dll`'s `RegisterAnimationSRTKeys` refuses a name already registered (the DLL logs the failure and goes on).
- **Stand:** a spawn stands at frame 0 of `P01` (STAND STILL) unless another animation is chosen. A model with no stand animation stands in its bind pose.

An EQG character plays the client's EQG animations:

- **Animation ids:** `eqgame.exe` keeps one table of 104 animation ids (`0xaae3e8`). Each id has an EQG name and the WLD animation it plays on a WLD model (`0xaaf428`): `/wave` is id 75, `WAVE` on an EQG model and `S03` on a WLD one.
- **Requests:** a request may give an EQG name (`STND`, `NRUN`), a WLD code, or a label. A code plays the first id mapped to it, so the default `P01` plays `STND`; an EQG name on a WLD model plays its id's code.
- **Lookup:** an EQG model plays `<name>_BA_1_<code>` (`EQGraphicsDX9.dll` `PlayAnimation`, `"%s_BA_1_%s"`), from the first archive in the load order that defines it, else from the first `OnDemandResources.txt` line naming it.
- **Files:** `.ani` animations hold, per bone, keys of time, translation, rotation, and scale. Skinned `.mod` and `.mds` files hold 56-byte bones (parent links and bind transform) and one 36-byte weight record per vertex (up to four bones). Every such file in the client parses exactly to its size.
- **Bones:** the DLL transposes each quaternion's matrix (`0x1003efc8`), a convention under which weighted vertices sit beside their bones. A vertex moves by its weighted bones from bind to pose.
- **Footing:** the DLL lowers `ROOT_BONE`'s keys by the model's `ROffset` (`0x1003cd5b`, every animation but `_MT_` ones). An animated EQG model's feet therefore sit `ROffset` below its origin, like a WLD model's.
- **Attached pieces:** a piece such as hair carries a subset of the skeleton's bones. It takes the skeleton's pose by bone name; a weighted bone that binds elsewhere than the skeleton's is an error.

### Spawn size

Spawns take the dumps' and the server's terms: `height` (EQEmu's size), `avatarHeight`, and `heading`. `eqgame.exe` `0x5a3f40` turns a spawn's height into the scale it draws the model at:

| Model | Zone without `NewEngineZone` | Zone with `NewEngineZone` |
|---|---|---|
| WLD | height / 5 | height / 6.5 |
| EQG | height * 1.3 / 6 | height / 6 |

- **EQG models:** the codes whose race `eqgame.exe` registers with flag 8. `eqRaces.py` holds all 859 of its race registrations (`0x50a440`).
- **`NewEngineZone`:** the zone header's flag (offset 692 of the RoF2 zone packet). The live dumps' `zoneHeaders` give it per zone; EQEmu sends false for every zone. `setZoneProperties` stores it with the zone.
- **`avatarHeight`:** how high the client stands the model origin above the ground: `Resources\moddat.ini`'s `ROffset` for the model (3.125 when it has none) times the scale. Luclin models' standing feet sit about 3 units below their origin.

The formula reproduces the `avatarHeight` of 16,926 of the 17,291 live-dump spawns whose model this client registers. The other 365 are races RoF2 registers as EQG models and live draws at WLD scale (`CAT`, `HLG`, `I25`, ...).

All four placement paths (`placeSpawn`, `placeDoor`, `placeObject`, and the scale figure) build through the same code. A model is indexed and built once:

- **Index:** `models\modelIndex.json` lists every archive's models and animations, rebuilt when the client listing changes.
- **Built models:** `models\built\<model>@<archive>[@appearance][@pose]`, rebuilt when the client's files change.

Placements take Blender values (`location`, `headingDegrees`) or EQ's (`x`, `y`, `z`, and `heading` in 512ths of a turn, as the server and the dumps give them). `eqgame.exe`'s heading toward a point (`0x4ef250`, which `/face` stores as the player's heading) is 0 toward +y and 128 toward +x. Through the axis swap, that is a turn of +heading about Z for a model whose front is +X. Measured doors confirm there is no quarter-turn offset, and claudelink's dumps agree: each spawn's, door's, and ground item's actor stands at its position and heading, the viewer's camera looks along its heading, and the shot of Highpass Hold of 2026-10-11 lines up with its prediction within a pixel.
